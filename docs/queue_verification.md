# Очередь пакетной обработки: как проверено

Что изменилось: `pipeline/job_scheduler.py` (очередь FIFO, по умолчанию одно видео за раз, число задаётся в
настройках `batch.max_concurrent_videos`), `pipeline/shared_models.py` (YOLO и Whisper грузятся один раз на очередь),
`llm/managed_provider.py` (`begin_use`/`end_use`/`release_if_unused`: LLM выгружается, только когда очередь пуста и
никто ею не пользуется). Раньше каждое видео сразу получало свой поток, а после любой задачи модель выгружалась.

## Прогон на реальном видео

Три куска по 4 минуты из `~/Видео/myvideo.mp4` (с 500-й, 1000-й и 1500-й секунды), добавлены разом в настоящее
`MainWindow` (offscreen), LM Studio на `localhost:1234`, модель `google/gemma-4-26b-a4b`. Скрипт: `scripts/verify_queue.py`.

| | |
|---|---|
| Состояние сразу после добавления | `Анализ`, `В очереди`, `В очереди` |
| Порядок запуска | job_1 → job_2 → job_3, пик одновременных задач: **1** |
| Загрузки моделей | YOLO: **1**, Whisper: **1**, LLM: **1 load / 1 unload** (выгрузка после последнего видео) |
| Клипы | 13 клипов, у всех 10 LLM-заголовков (`llm_errors` пуст), ни одного «Момент N s» по умолчанию |
| Память (MemAvailable) | старт 19.5 ГиБ, минимум 8.1 ГиБ (пик падения 10.9 ГиБ вместе с загруженной LLM) |
| Время | 1358 с на 3×4 мин видео (13 клипов) |

Оговорка про память: на момент проверки работали ещё `ollama` и `open-webui`, и штатный запас под пайплайн (6 ГиБ)
не оставлял места ни одной из трёх моделей LM Studio («доступно 19.3 ГиБ, резерв 6.0 ГиБ, gemma нужно ~14.4 ГиБ»).
Для прогона запас снижен до 4.5 ГиБ (`--reserve-mib 4608`), при этом скрипт сам прервал бы прогон при
MemAvailable < 1.2 ГиБ (не потребовалось). Без LLM такой же прогон (754 с) дал те же порядок и число загрузок YOLO/Whisper,
пик падения памяти пайплайна 3.7 ГиБ.

## Интерфейс на длинном списке

`BatchQueueView` рисует прогресс делегатом вместо `QProgressBar` на каждую строку, колонки фиксированной ширины
(`ResizeToContents` пересчитывал ширину по всем строкам при каждом обновлении: 6.2 с на 1000 обновлений).

| видео | добавить в таблицу | обновления прогресса всех строк | планировщик (submit+done) |
|---|---|---|---|
| 100 | 6 мс | 2.5 мс | 0.1 мс |
| 1000 | 8 мс | 6.4 мс | 0.4 мс |
| 5000 | 32 мс | 28 мс | 2.1 мс |

## Найденная и исправленная ошибка

При появлении результатов второго видео интерфейс замирал навсегда: `QMediaPlayer.setSource` при уже открытом
клипе ждёт поток декодера, а тот при разрушении объектов берёт GIL, который держит вызвавший Python-код (взаимная
блокировка, воспроизводится на реальных h264 1080×1920 клипах). `PreviewPlayer` теперь передаёт источник нативной
queued-связью сигнала со слотом; регрессионный тест `test_switching_clip_after_playback_started_does_not_freeze_the_ui`
без исправления зависает (проверено), с ним проходит. Дополнительно новые результаты очереди больше не перехватывают
выбор, если пользователь уже смотрит другой клип.
